thread_pool — work-stealing estilo arena

Pool oficial: filas compartilhadas (shards) + deque Chase-Lev local + concorrência dinâmica (core/reserva) + worker elástico para tasks longas.

Fonte: Xplatbase/Xplatbase/src/thread_pool.c · thread_pool.h · run-to-completion · C (Windows/Linux).

VISÃO Arquitetura geral

O submit externo (de uma thread produtora) vai para um conjunto pequeno de filas MPMC compartilhadas (shards); qualquer worker puxa de qualquer shard — a task não fica presa a um dono. Tasks geradas de dentro de outra task (spawn) usam o deque Chase-Lev local do worker. Um esquema core/reserva mantém só ~75% dos cores quentes no caso comum, e um worker elástico entra em cena quando tasks longas prendem workers.

  • Sem dono por fila: tasks externas vivem em shards compartilhadas → uma task longa ocupa um worker, mas não bloqueia fila nenhuma (não há head-of-line; os outros workers seguem puxando).
  • Submit barato em regime quente: com workers core ativos, o produtor só enfileira; só acorda alguém se houver core parqueado.
  • Concorrência dinâmica: core/reserva mantém ~75% CPU no flat e usa todos os cores no spawn, sem nº fixo de workers.
  • API dupla: instância global (criada no platform_init) para uso direto, e API relative para criar pools avulsos.

01 Modelo de execução núcleo

O pool é run-to-completion: cada task é uma função void(*)(void*) que roda do início ao fim num worker (não suspende). É a escolha certa para latência extrema de tasks curtas — sem máquina de estado/alocação por task de um runtime async. Para muitas tasks bloqueantes/longas, isole-as (ver §14).

Threads do pool (16 cores, defaults): 16 workers normais (11 core + 5 reserva) + 16 elásticos (parqueados) + 1 monitor. No estado comum só ~11 ficam quentes; o resto dorme.

02 Estrutura: workers, shards, deque núcleo

  • Shards (n_shards = cores/4, mín. 1): filas MPMC (ring Vyukov) compartilhadas, alvo do submit externo. Capacidade POOL_SHARD_CAP (4096) cada.
  • Workers (n_total = n_workers + n_elastic): índices [0,n_core) = core, [n_core,n_workers) = reserva, [n_workers,n_total) = elástico. Defaults: n_workers=cores, n_core=cores·7/10, n_elastic=cores.
  • Deque Chase-Lev por worker: pilha lock-free para spawn — o dono faz push/take (LIFO) no bottom sem CAS no caso comum; ladrões roubam do top (FIFO, com CAS).
  • Contadores de pending (ctrs[], tamanho n_shards+n_total): cada task carrega o índice do contador a decrementar ao terminar (ver §9).
  • Monitor: thread que detecta workers presos em tasks longas e aciona os elásticos.

03 Submit externo (arena) núcleo

Chamado por uma thread que não é worker do pool. Faz round-robin nas shards e empurra (MPMC). Em regime quente os workers se auto-servem das shards, então o produtor não acorda ninguém — só dispara um wake (round-robin entre os core) se houver core parqueado. Se a shard estiver cheia, faz backpressure (espera, nunca falha — exceto em shutdown).

// caminho externo (resumo)
s = submit_rr++ % n_shards;
ctrs[s]++;
if (push_mp(shards[s], task))            // MPMC
    if (n_parked_core > 0) wake(core[wake_rr++ % n_core]);

04 Submit reentrante / spawn núcleo

Quando pool_submit é chamado de dentro de uma task (task que cria task), o pool detecta que a thread atual é um worker (g_pool_self) e empurra no deque LOCAL dele — push Chase-Lev sem CAS e sem wake. O próprio worker faz take() LIFO em seguida (cache-quente); os outros roubam o excedente. Se o deque local encher, a task roda inline (evita self-deadlock do submit reentrante).

O deque local é o caminho de menor custo do pool. É por isso que cargas fork/join (spawn) escalam bem: o trabalho fica local e cache-quente, com steal só do excedente.

05 Work-stealing núcleo

O worker ocioso busca trabalho nesta ordem (pool_try_get):

  • 1. Deque próprio — take() LIFO (spawn local).
  • 2. Shards — varre as n_shards filas compartilhadas a partir de um cursor (trabalho externo).
  • 3. Steal — rouba do top dos deques dos outros workers (inclui elásticos), a partir de um cursor rotativo.

Como steal usa o topo do deque e push/take do dono usam o fundo, dono e ladrão tocam pontas opostas — contenção mínima.

06 core / reserva elasticidade

Concorrência dinâmica sem fixar nº de workers:

  • core (cores·7/10): recebem o submit externo (são acordados) e, quando ociosos, fazem spin progressivo antes de parquear — baixa latência de pickup. Contam em n_parked_core ao parquear.
  • reserva (o restante dos n_workers): park-first — quando ociosos, dão uma varredura de steal e parqueiam, sem busy-spin. Não são acordados pelo submit; só engajam quando acham backlog na re-checagem (a cada ~1ms).
Efeito: no flat (produtor externo) só os ~11 core ficam quentes → ~75% de CPU com cauda baixa (sem a oversubscription que inflaria a cauda). No spawn, o trabalho é local e a reserva engaja → usa todos os cores.

07 Worker elástico & monitor elasticidade

Protege a latência das tasks curtas quando workers ficam presos em tasks longas (perfil "rápida pode virar lenta"):

  • Cada worker mantém done_count (progresso) e in_task, ambos single-writer (custo ~zero no hot-path).
  • O monitor (a cada POOL_MON_MS = 5ms) marca como preso quem está in_task e cujo done_count não mudou desde o tick anterior (task durando > ~1 tick sem terminar).
  • Se há ≥ POOL_STUCK_MIN (2) presos e backlog nas shards, acorda 1 worker elástico (criado além dos cores) para drenar as curtas.
  • Os elásticos se aposentam (re-parqueiam) ao não acharem trabalho por um tempo.

Para tasks longas bloqueantes (I/O), o elástico recupera o core liberado. Para CPU-bound, sobre-subscreve (time-slice) mantendo as curtas responsivas. Não há preempção; ver limites em §14.

08 Spin progressivo & wake núcleo

Worker core ocioso: POOL_SPIN_PAUSE pausas (×512) → POOL_SPIN_YIELD yields (×64) → POOL_SPIN_SLEEP0 (×8), re-tentando try_get a cada iteração; se nada, parqueia em WaitOnAddress/futex com timeout POOL_PARK_TIMEOUT_US (1ms, como rede de segurança). O wake do submit é direcionado e condicional (só se há core parqueado), mantendo o caminho quente sem syscall.

09 Contagem de pending núcleo

Em vez de um contador global (que geraria ping-pong de cache), cada task carrega o índice do contador a decrementar (ctr): shards usam ctrs[0..n_shards-1]; o deque local do worker i usa ctrs[n_shards+i]. Quem roda a task decrementa ctrs[ctr] — correto mesmo com steal (o decremento segue o contador gravado na task). pool_wait_idle soma todos os contadores.

10 API: global e relative núcleo

Duas formas de uso. A global usa uma instância única (GlobalPool) — não precisa passar o pool. A relative opera sobre um pool criado avulso (passado por parâmetro).

Instância global

FunçãoDescrição

pool_submit(minha_task, arg);
pool_wait_idle();

// uso avulso
ThreadPool* p = pool_create_relative(8);
pool_submit_relative(p, minha_task, arg);
pool_wait_idle_relative(p);
pool_destroy_relative(p);

11 Inicialização global núcleo

platform_init() (em xplatbase.c) chama pool_create() — ao inicializar a biblioteca, a instância global já fica pronta para uso direto via pool_submit(...). GlobalPool é estático ao módulo; a criação não é thread-safe (espera-se que platform_init rode uma vez no startup).

void platform_init() {
    if (platform_initialized) return;
    ...
    pool_create();          // instancia global pronta
    platform_initialized = true;
}

14 Limitações & quando isolar limites

  • Tasks longas em massa: uma task longa não bloqueia fila (sem dono), mas ocupa o worker. Muitas longas CPU-bound simultâneas saturam os cores (limite físico — sem preempção). Muitas bloqueantes prendem workers com cores ociosos.
  • Recomendação: mantenha o pool para o caminho curto/latência-crítico; para trabalho longo/bloqueante em volume, use um pool separado ou um reactor (IOCP/epoll) para a prontidão de I/O.
  • Não inclui (presentes no WSPool antigo, hoje em src/versions/): pool_stats/telemetria, shutdown com drain/timeout configurável, detecção de force-kill/pool envenenado, hook de log, e a suíte de determinismo/bugs. Portáveis se necessário.

Explicação dos resultados

  • Tasks curtas / triviais (flat, rapida/*, satur/*, rajada-curta): o oficial vence em throughput — +9% no flat e +19–25% nos de saturação (satur/ultra 2.73 vs 2.21 Mtask/s) — e a ~75% de CPU contra ~94–99% do TBB. O p50 fica em 0.6µs (vs 1.0µs do TBB). É o efeito do submit barato (arena, sem wake em regime quente) + core/reserva (só ~11 cores quentes).
  • Tasks com trabalho real (media/*, mista/*, mista-massiva/*): throughput ~empata, mas a latência é dramaticamente menor — p50/p99 3–10× abaixo do TBB. Ex.: media/ultra p50 31ms vs 201ms (6.5×); mista/ultra 15ms vs 140ms (~9.5×); massiva/ultra 19ms vs 197ms (~10×). Como as shards são drenadas perto da ordem de submissão, a espera média das tasks é muito menor que no enqueue do TBB.
  • lento-misto (perfil "rápida pode virar lenta"): o worker elástico cumpre o papel — p50 das curtas 23.6ms vs 534ms do TBB (~22×). As tasks longas (CPU-bound, ~2000×8ms) seguem ~1s no p99/max — limite físico (16 cores, sem preempção); o elástico não acelera as longas, ele protege as curtas.
  • spawn-arvore (task dentro de task): único ponto fraco — TBB ~15% à frente (15.6 vs 13.6 Mtask/s), latência par. O scheduler de arena do TBB ainda leva vantagem no fork/join puro. Fora do caso de uso típico (protocolos = submit externo).
  • WinTP: perde em quase tudo. Só usa pouca CPU nos triviais (~20%, porque parqueia agressivo), pagando com p50 ~10µs (vs 0.6µs) e latências horríveis no spawn (p50 253ms) e sob carga.
  • Sobre o max: é 1 amostra (ruidoso); por isso reportamos max10 (média dos 10 piores), que é estável e mostra a cauda real — no oficial fica no nível do TBB nos triviais e bem abaixo nas cargas com trabalho.
Resumo: para tasks curtas com submit externo (o caso de protocolos de baixa latência) o oficial entrega mais throughput a menos CPU e latência muito menor sob carga que o TBB, além de proteger as curtas quando tasks viram longas. O único trade conhecido (spawn) está fora desse perfil.
